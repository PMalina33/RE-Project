# Week 1 — Initial Discovery
## 1. Facts
- Presently equipment can be double booked.
- At the moment bookings are managed using a mixture of sources, email, spreadsheet, informal arrangements.
- Looking for a system to solve problems outlined.
- Both students and staff should be allowed to book shared equipment on new system.
- Information on who to contact is currently unclear.
## 2. Assumptions
- Contact information to be displayed clearly on new system.
- Show only available equipment to book.
- Digital booking system to be implemented.
- Equipment cannot be double booked.
## 3. Unknowns
- What sort of equipment is more popular when booking?
- What digital system wants to be created?
- Who should be contacted about the equipment?
- Should there be an extended date of return option?
## 4. Stakeholders
- What might each stakeholder need or care about?
Student: Easy booking, availability, return date
Staff: Availability, easy monitoring, overdue returns
IT: Data updates, technical issues, security
Equipment provider: Amount supplied, quality of equipment, issues with equipment
College Management: Damaged equipment, easy monitoring, amount of equipment booked
## 5. Goals
- System should help staff manage bookings a lot easier.
- System should be easy to use and understand.
- System should clarify equipment availability.
## 6. Scope
Likely to be part of the problem:
- Double bookings.
- Unknown availability.
- Unclear equipment return dates.
Cannot currently assume are requirements:
- Staff get priority.
- Equipment booking can be extended if close to return date.
## 7. Candidate Requirements
Functional:
- System should allow authorised users to request equipment for a specific date/time.
- System should allow staff users to access return logs. 
- System should record equipment available and not available.
- System should allow users to search for desired equipment.
- System should not allow double bookings to take place.
Non-functional:
- Users logins should be protected/encrypted.
- System should be available/acessable to use at any time.
## 8. Requirement Surgery
R1: The system should be easy to use.
Weak in what way: not specific on who the targeted users would be to determine the difficulty of use.
Rewritten: The system should allow both students and staff to navigate and book with ease.
R2: The system should be secure.
Weak in what way: not specific on where the security should come from, what should be protected.
Rewritten: System should encrypt users logins and personal information related with their data.
